# 管理长任务

使用 Skill 约束执行流程，使用一份中文 Markdown 账本保存当前任务的动态状态。不得把任务状态写回 Skill，也不得只在对话中保存长任务进度。

## 确认启用方式

- 用户明确说“启动需求跟踪”“启用需求跟踪”或表达同等含义时，无论任务大小都立即启用本 Skill，创建或接管一份任务账本。
- 用户明确要求长任务、持续推进、任务跟踪、分阶段执行或上下文压缩后继续，或任务明确跨调查、设计、实现和验证阶段、涉及多个模块、需要反复诊断、外部等待或跨会话继续时，直接启用本 Skill。
- 如果现有信息不足以可靠判断轻量任务或长任务，先询问用户是否启用需求跟踪。在用户确认前不创建账本，也不因“不确定”自行升级。
- 用户在任务进行中要求启动或启用需求跟踪时，先创建或接管账本并补录已有目标、事实、变更和验证，再继续实质性修改。

## 启动或恢复

1. 读取用户级和当前路径适用的 `AGENTS.md`。
2. 检查 `git status`、相关差异、仓库说明和可用验证方式，识别用户已有改动。
3. 在仓库约定位置查找同一用户结果的活动账本；没有约定时使用 `doc/tasks/`。
4. 找到账本时完整读取并与工作区对账，不得新建竞争账本。
5. 没有账本时，在首次实质性修改前根据 `assets/task-ledger-template.md` 创建 `doc/tasks/<task-id>.md`。
6. 使用中文记录用户最新指令、稳定目标、范围、非范围、约束、验收和计划。
7. 记录启用方式：用户强制、明确长任务条件或用户确认。
8. 只将一个计划步骤设为 `进行中`，并写明一个可立即执行的“下一步唯一动作”。

任务标识使用稳定、简短的英文小写连字符形式，例如 `2026-08-16-cache-recovery`。用户修正同一结果时继续维护原账本，只有目标真正独立时才创建新账本。

## 落地五类核心产物

在同一账本中维护以下独立章节，不得静默删除或合并成模糊摘要：

1. `需求定义`：记录背景、目标、范围、非范围、约束和可验证验收标准。为每项实质需求分配 `REQ-###`。
2. `总体架构`：记录当前真实入口、目标结构、模块边界、关键流程、依赖和架构决策。完成必要调查后、相关实现前建立。
3. `单元设计`：记录受影响单元、文件位置、职责、输入输出、正常与异常处理、兼容要求和验证方式。为单元分配 `UNIT-###`。
4. `执行任务`：记录步骤、状态、文件范围、关联需求、完成条件、当前交接和下一步唯一动作。为步骤分配 `TASK-###`。
5. `测试与验证`：记录测试目标、方法或准确命令、预期、实际结果、证据和未执行原因。为测试分配 `TEST-###`。

某类产物确实不适用时，保留对应章节并写明“不适用”、理由和可核查依据。需求、架构或单元设计改变后，重新检查任务、测试和追踪关系是否仍然有效。

## 建立端到端追踪

维护一张追踪矩阵，将每项 `REQ-###` 关联到：

- 验收标准；
- 架构或 `UNIT-###`；
- 一个或多个 `TASK-###`；
- 实现文件、配置或 `IF-###`；
- 一个或多个 `TEST-###`；
- 最终结果和证据。

不得仅因为章节存在就认为需求已经覆盖。准备门禁检查每项需求是否有任务和测试计划；完成门禁检查每项需求是否有实现与通过证据。需求被取消或替代时保留编号，并记录状态和替代关系。

## 记录接口

新增或修改跨单元、进程、服务、协议、配置契约或用户可见接口时，为其分配 `IF-###`，记录：

- 接口名称、调用方和提供方；
- 输入、输出、错误和兼容契约；
- 实现文件或配置位置；
- 关联需求、任务和测试；
- 当前状态与验证证据。

任务不涉及接口或契约变化时，在接口记录中写明“不适用”和依据，不创建空接口编号。

## 记录决策与冲突

对影响范围、架构、接口、兼容、测试、风险或后续动作的选择分配 `DEC-###`，记录触发原因、采用方案、证据、替代方案、影响和替代关系。小型局部实现细节无需记录。

用户指令、适用规则、账本、代码事实或并发改动发生冲突时分配 `CON-###`，记录冲突输入、优先级判断、处理结论、理由、影响产物和状态。以更高优先级指令、用户最新方向和当前可验证事实解决冲突，不让历史账本覆盖新指令。

决策被新证据推翻时不得删除旧记录；将其标记为“已替代”，并链接新的决策编号。

## 执行准备门禁

首次实现前执行准备门禁，至少检查：

- 用户最新目标、范围、非范围和约束已记录；
- 验收标准可观察、可测试；
- 必要的总体架构和对应单元设计已达到可实现程度；
- 每项有效需求已有任务、文件或接口范围和测试思路；
- 工作区基线和用户已有改动已识别；
- 高风险变更已有回滚思路；
- 没有未解决且会改变实现方向的冲突。

门禁结论只使用 `通过`、`不通过`、`有条件通过`。`不通过` 时不得开始相关实现；`有条件通过` 必须记录条件、影响和关闭要求。

## 执行工作循环

重复以下循环，直到完成或出现真实阻塞：

1. 重读当前交接、有效决策、追踪矩阵和进行中的任务。
2. 为当前任务收集足够证据，区分已验证事实、假设和未知项。
3. 执行能够推进验收条件的最小连贯修改，不扩大未授权范围。
4. 运行与风险相称的验证。
5. 更新五类产物、追踪、接口、决策、缺陷、回滚、事实、风险和门禁状态。
6. 形成检查点，设置下一个唯一动作；仍获授权且方向清晰时直接继续。

通过对话进度更新帮助用户观察过程，但以仓库账本作为持久状态源。

## 管理测试、缺陷与回滚

测试失败时先判断是实现缺陷、环境问题、既有失败还是测试假设错误，并保存准确证据。确认或高度可信的产品问题分配 `DEF-###`，关联需求和测试，记录严重程度、现象、根因、修复状态、修改位置和复测证据。

不得通过删除测试、放宽断言或隐藏错误制造通过结果。未执行测试必须记录原因、影响、替代证据和后续动作。

配置、数据结构、迁移、依赖、部署或高风险行为发生变化时记录回滚方案，包括触发条件、回滚步骤、数据或兼容影响、回滚后验证和责任边界。无需回滚的纯文档或低风险变更写明“不适用”和依据。

## 建立检查点

发生以下任一事件后立即更新账本：

- 用户更改、缩小或扩大需求；
- 计划步骤完成、取消、阻塞或执行方案改变；
- 已验证事实推翻假设、架构、单元设计或决策；
- 重要修改、测试、缺陷修复或回滚信息产生；
- 命令将等待外部过程或可能超过当前交互周期；
- 工作即将转交、暂停、压缩或结束。

检查点只保存结论、证据、影响和下一步，不粘贴大段日志或记录无价值的命令流水。账本变长时，把旧检查点归并到正式记录中。

## 处理用户转向

收到用户替换、修正或追加指令时：

1. 在继续修改前更新“用户最新指令”。
2. 记录该指令对需求、架构、单元、任务、测试、决策和门禁的影响。
3. 保留仍符合新方向的有效成果和证据。
4. 将被替代的任务设为 `已取消`，更新追踪关系，不沿旧计划继续。
5. 只有缺失选择无法自行发现且不同答案会实质改变结果时才向用户提问。

账本记录需求，但不产生高于用户的新权限。

## 从压缩或转交中恢复

上下文已被摘要、信息不完整或任务来自其他执行者时，在新修改前：

1. 重读用户级和当前路径适用的 `AGENTS.md`。
2. 重读本 Skill 和完整活动账本。
3. 检查 `git status`、相关差异、关键文件和最近测试产物。
4. 对照用户最新指令、五类核心产物、追踪矩阵、有效决策、冲突、门禁和工作区事实。
5. 修正账本中已过期、矛盾或无法被当前证据支持的状态。
6. 只保留一个进行中任务和一个下一步唯一动作。
7. 从第一个证据不足或未完成的任务继续，不重复已有有效证据的工作。

不得仅凭上下文摘要继续。恢复期间工作区仍在变化时，视为可能存在已授权并发过程；稳定后重新读取账本、状态和差异，不覆盖并发改动。

## 管理阻塞

声明阻塞前尝试安全、授权且不改变目标的替代路径。发生阻塞时记录：

- 精确阻塞条件和证据；
- 对需求、追踪和门禁的影响；
- 仍然有效的已完成工作；
- 已失败的尝试和失败原因；
- 所需的最小用户或外部动作；
- 阻塞解除后的下一步唯一动作。

不得因为时间、上下文或令牌预算不足而将未完成工作标记为已完成。

## 执行完成门禁

交付前逐项检查：

- 用户最新目标和全部有效 `REQ-###` 已有验收结论；
- 需求、架构、单元、任务、文件或接口、测试和证据追踪闭合；
- 相关测试已运行，未运行项的原因和影响准确；
- 失败测试与 `DEF-###` 已处理或作为用户接受的遗留风险记录；
- 有效决策、冲突、回滚方案、风险和阻塞状态已更新；
- 最终差异不存在范围漂移、无关回退、调试残留或意外格式化；
- 账本与工作区一致，完成摘要准确，下一步唯一动作为 `无`。

完成门禁结论只使用 `通过`、`不通过`、`有条件通过`。条件未关闭时不得将整体任务设为 `已完成`。

## 保持账本可信

- 输出文档使用中文；代码、路径、命令、配置键、接口名和日志原文按原文保留。
- 任务和计划状态只使用：`待开始`、`进行中`、`已阻塞`、`已完成`、`已取消`。
- 准确记录实际命令和结果，不得声称未运行的测试通过。
- 不写入密钥、凭据、个人数据、大段原始日志或无依据猜测。
- 证据优先使用路径、提交标识、命令摘要、测试名称和可复查产物。
- 每个用户结果只维护一份账本，不模拟 Architect、Code、Debug 或门禁裁判角色。
