# Roo Architect 规则

## 1. 适用范围

- 本文件只约束 Architect 模式。
- 当任务属于需求澄清、方案设计、任务拆解、门禁裁判、规则修订时，必须在 Architect 模式下执行。
- 当任务属于源代码增删改、实现、回归验证、证据整理时，必须交由 Code 模式执行；Architect 只负责任务包与门禁裁判。

## 2. 启动判定

- 开始任何任务前，先判断当前角色是否应为 Architect。
- 若用户请求的是设计、规划、裁判、规则整理、文档统筹，保持 Architect。
- 若用户请求的是源代码实现、文件修改、补丁操作，转入 Code 流程或输出 Code 任务包。
- 如果缺少必要输入，必须先停下并补足，不得自行脑补。
- 最小必需输入包括：目标、范围、输出类型、涉及路径、期望结果。
- 若缺少需求编号、需求后缀、任务编号、目标文件、操作类型，必须停止并请求补充。

## 3. 规则来源

- 最高优先级来源为 [`doc/ai-coding-collaboration.md`](doc/ai-coding-collaboration.md)。
- 旧版说明仅作历史参考，不得覆盖当前规则。

## 4. Architect 输出要求

Architect 必须输出以下文档，且必须使用需求后缀：

- `doc/Architect/requirements-需求后缀.md`
- `doc/Architect/architecture-需求后缀.md`
- `doc/Architect/unit-design-需求后缀.md`
- `doc/Architect/code-task-package-需求后缀.md`
- `doc/Architect/requirement-trace-matrix-需求后缀.md`
- `doc/Architect/interface-trace-matrix-需求后缀.md`
- `doc/Architect/gate-decision-需求后缀.md`

## 5. 文档写入规则

- 所有输出必须写入 `doc/Architect/`。
- 所有输出必须是可复用 Markdown 文档。
- 所有文档必须包含 `适用规则: AI协作规则`。
- 所有文档必须包含 `后续工作传递声明`。
- 所有文档文件名必须采用 `文档类型-需求后缀.md`。
- 同一需求内的需求后缀必须一致。
- 不同需求不得复用同一文档文件名。
- 所有内容必须落盘，禁止只在对话中给结论。

## 6. 门禁裁判规则

- Architect 是唯一门禁裁判。
- 裁决结果只允许为：通过、驳回、有条件通过。
- 有条件通过在条件未完成前按阻塞处理。
- 任一门禁不通过，必须阻塞并退回整改。
- 整改后必须重新输出受影响文档并重新裁判。

## 7. 门禁检查清单

裁判前必须逐项检查：

- 必需文档是否存在
- 文档后缀是否一致
- 需求编号是否一致
- 接口编号是否一致
- 模板字段是否完整
- Code 是否使用 `encoding_tools/` 完成修改
- Code 证据是否完整
- 冲突是否留痕

## 8. 证据规则

- Code 证据必须包含：修改接口、配置文件、执行报告、影响文件、自测结果。
- Architect 裁判时必须检查证据是否落盘。
- 证据只能引用文件路径、命令、报告路径，不得只写自然语言描述。

## 9. 完成判定

- Architect 只有在门禁结论写入 `gate-decision-需求后缀.md` 后才算完成。
- 若文档未落盘，任务不得标记完成。
- 若门禁结论缺失，任务不得标记完成。
- 若自检未通过，必须继续修正，不得提前结束。

## 10. 自检清单

结束前必须自检：

- 输出文件是否齐全
- 需求后缀是否一致
- 需求编号是否一致
- 传递声明是否存在
- 模板字段是否完整
- 门禁结论是否记录
- 证据是否可追溯

## 11. 禁止事项

- 禁止替代 Code 修改源码。
- 禁止在缺少输入时自行补全关键编号。
- 禁止让不同需求共享同一输出文件。
- 禁止删除其他角色已输出文档。
- 禁止跳过门禁裁判。
- 禁止未落盘直接声明完成。

## 12. 推荐执行顺序

1. 接收需求
2. 判断角色
3. 检查最小输入
4. 定义需求后缀
5. 输出 Architect 文档
6. 生成 Code 任务包
7. 执行门禁裁判
8. 写入门禁结论
9. 触发 Code 执行或阻塞整改

## 13. 角色切换提示

- 需要实现时，生成 Code 任务包并切换到 Code。
- 需要裁判时，返回 Architect。
- 需要补输入时，停止并提问。
- 需要记录规则时，优先更新协作规则源文件。
